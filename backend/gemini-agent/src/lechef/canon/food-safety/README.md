# data/food-safety — the FridgeLuck food-safety canon

One canonical rulebook and linter for the whole product. No module keeps its own
temperature table, phrase list or spoilage policy: consumers call the
`FLFoodSafety` package or run the `fl-safety-lint` CLI. This directory is the
source of truth; `packages/FLFoodSafety` is its executable form.

Owner: the food-safety canon task (draft PR superseding #97, which this branch
takes over from head `a63fd2ff4e0c40c5b53b5e62730f21f1b97b39b1`). Change control:
draft PR into `alpha` only.

## Layout

| Path | What it is |
| --- | --- |
| `rules.json` | The rulebook: doneness, rest, reheating, cooling, storage, thawing, cross-contamination, hygiene, high-risk notes. Every rule cites a fetched primary source. |
| `SCHEMA.md` | The `rules.json` format and its validation contract (strict decoder: unknown keys fail). |
| `SHELF-LIFE.md` | FoodKeeper-sourced quality windows — quality guidance, never a safety certificate. |
| `COPY.md` | Phrasing guide for LeChef and UI copy: thermometer-first doneness, the never-say list, and the spoilage/use-it-up policy. |
| `BUNDLED-RECIPE-AUDIT.md` | Generated audit of the bundled recipes (regenerated by the CLI). |
| `conformance/` | JSON fixtures pinning linter and copy-lint behaviour: positive cases and true negatives. |

## The linter contract (strict, fails closed)

A doneness check **counts** only when the instruction text the user reads:

1. names a food thermometer ("thermometer", "instant-read thermometer",
   "meat thermometer", "probe"), and
2. states an internal temperature at or above the class minimum (°F or °C), and
3. states the rest time where the class requires one (3 minutes for whole cuts
   of beef, pork, veal and lamb).

Additionally:

4. Oven or pan temperatures never count as doneness checks ("bake at 400°F"
   decides nothing about doneness).
5. Metadata the text does not show does not count — a record's structured safety
   field must appear in the instruction text the user reads; if it exists only in
   metadata, that is a finding, not a pass.
6. An ingredient that cannot be classified to a doneness class is **flagged for
   review**, never passed.
7. When anything is uncertain — missing rules file, unparseable record, unknown
   class — the linter fails closed: the finding says what is missing. It never
   defaults to pass.

The linter keeps flagging the older failure classes as well: doneness by
appearance (colour, "no pink", clear juices, firmness), time-only protein
cooking, raw-egg dishes without the pasteurized-egg requirement, ambient
thawing, leftovers held out beyond the cooling window, and reheating without a
thermometer check.

## Finding format

Every finding — package API, CLI output, audit rows, and per-PR fix lists —
carries one exact fix:

```
file · record id · field · current text (verbatim snippet) · required change (exact rewrite + rule id + citation)
```

"Flag for review" findings state what a reviewer must decide; they never guess.

## Spoilage and use-it-up policy

Advice may cover using food **before** it passes its quality window
(`SHELF-LIFE.md`). Advice may not salvage food that is spoiled, slimy, decaying,
sprouted beyond a cited exception, or off-smelling, and may not rely on smell as
a safety test. `COPY.md` carries the policy and the patterns; the copy lint
enforces them.

## Conformance

`packages/FLFoodSafety` tests assert every clause above against `conformance/`
fixtures, and `fl-safety-lint` replays the same fixtures from the command line.
A non-zero exit means findings exist; clean input exits zero.
