## 2. Fail-open behavior found

1. **Dietary restrictions are never evaluated in code.** `ingredientPolicyFor` builds `{ avoided: request.avoidIngredients, allowed: [...supplied, ...staples] }`. The user's `dietaryRestrictions` (contracts.ts line 106) is only joined into a prompt string — `dietary_restrictions: ${restrictionsText}` (recipeService.ts lines 303–304, 333). Whether the model honors it is unverifiable; the accept path (`isAllowedFood` + `firstAvoidedMention`) checks **only** the client's `avoidIngredients` list. A user whose profile carries a milk allergy but whose `avoidIngredients` array says `["mango"]` gets recipes with **cream cheese**; a wheat+soy avoider gets **tamari/soy sauce**; a vegetarian gets **lard** and **Worcestershire sauce**. All pass the screen: they are supplied, or declared in `ingredientsUsed`, or covered by nothing-but-nothing because no restriction tokens exist in code.
2. **Absence from the lexicon/policy means allowed.** The module's own doc comment (lines 38–46) concedes: foods outside the frozen lexicon are screened only when the model declares them; compounds, synonyms and brands are unmatched; "This is NOT an allergy-safety or complete grounding guarantee." An undeclared allergenic ingredient (e.g. the model writes "shoyu" instead of "soy sauce") is allowed.
3. **Supplied pantry items bypass restriction checks entirely.** `allowed: [...supplied, ...]` — if the user's pantry contains soy sauce, any recipe using it passes the declared-ingredient gate with no restriction evaluation at all.
4. **No unknown state exists.** There is no representation for "we don't know what's in this ingredient" — the only outcomes are matched/missed against string lists, so an ingredient with no facts is silently treated as safe.

## 3. Exact changes needed (file by file)

Goal: restriction enforcement in code, fail-closed, with the shared dataset as the single facts source; unknown ⇒ reject-and-ask, never allowed; meal restrictions are the union of every eater's restrictions (`FLRestrictions.union` semantics — for the household session, union all eaters' restrictions before evaluating).

### 3.1 New module `backend/gemini-agent/src/services/ingredientFacts.ts`

Load `data/ingredient-facts` once and expose a fail-closed evaluator mirroring the pinned contract:

```ts
// data/ingredient-facts is loaded at build/startup; resolve via identities.json
// (canonical key, synonyms, aliases), then read facts.json for the resolved key.
export interface Restrictions { allergens: Set<string>; diets: Set<string> } // FLAllergen / FLDiet vocab
export function unionRestrictions(rs: Restrictions[]): Restrictions;        // FLRestrictions.union
export type Evaluation =
  | { kind: "allowed"; evidence: unknown[] }
  | { kind: "violated"; reason: string; component: string }
  | { kind: "unknown"; missing: string[] };                                 // ⇒ ask the user

export function evaluate(ingredient: string, restrictions: Restrictions): Evaluation;
```

Semantics to mirror (tested by the shared conformance cases): fail closed on unresolvable names; `violated` > `unknown` > `allowed` ordering; `variable`/unsourced properties are `unknown`, never `false`; compounds stay compounds (soy sauce ⇒ soy+wheat; generic tamari ⇒ soy with gluten unknown unless a `label` evidence entry says otherwise).

### 3.2 `backend/gemini-agent/src/types/contracts.ts`

- Parse `dietaryRestrictions` into the `FLRestrictions` vocabulary (validate tokens; an unrecognized restriction string is `unknown`, not ignorable) and add it to `RecipeGenerationRequest`'s decoded, required-on-the-enforcement-path form (keep it optional on the wire, but the policy must distinguish "absent" from "evaluated empty").

### 3.3 `backend/gemini-agent/src/services/recipeService.ts`

- `ingredientPolicyFor`: add `restrictions: Restrictions` to `IngredientPolicy`, built as `unionRestrictions([...householdEaters.map(e => e.restrictions), parsedDietaryRestrictions])`.
- Add a restriction screen beside the avoid screen, applied to **every** ingredient channel — supplied foods, staples, declared `ingredientsUsed`, and lexicon hits in title/instructions:

```ts
// before — nothing evaluates dietaryRestrictions
// after
function firstRestrictedFood(text: string, policy: IngredientPolicy): { food: string; violation: string } | undefined {
  for (const food of foodsIn(text)) {
    const verdict = evaluate(food, policy.restrictions);  // FLEvaluation — typed union
    switch (verdict.kind) {                               // dispatch on the DISCRIMINANT
      case "violated":                                    // (switching the returned OBJECT
        return { food, violation: `${verdict.reason} (component: ${verdict.component})` };
      case "unknown":
        return { food, violation: `unknown-ingredient-facts: missing ${verdict.missing.join(", ")}` }; // ask, never serve
      case "allowed":
        break;                                            // this food is fine — keep scanning
      default: {
        const exhaustive: never = verdict;                // compile error if a kind is ever added
        return { food, violation: `unhandled evaluation: ${String(exhaustive)}` };
      }
    }
  }
  return undefined;
}
```

The wrong shape to avoid: `switch (evaluate(food, policy.restrictions)) { case "violated": … }` switches the returned **object** against string literals — no case can ever match, the loop always falls through, and `firstRestrictedFood` returns `undefined` (a silent pass) for every input. The wrapper must itself reject: the accept path (request handling at lines 303–333) treats a defined `firstRestrictedFood` result as a rejection and `undefined` as the only pass, so both `violated` and `unknown` block the recipe **at the wrapper level**, not merely inside the evaluator.

- Reject with a static public-safe message mirroring the existing rejection style (lines 147–158): `"Recipe rejected: an ingredient conflicts with the household's dietary restrictions."` / `"...could not be verified against known ingredient facts."`
- Staples: keep the four-item staple list as *supplied-by-default*, but each staple still goes through `evaluate` — the dataset covers them, and any future staple addition is screened instead of trusted.

### 3.4 `backend/gemini-agent/src/agent/systemPrompt.ts`

Keep the prompt line, but demote it: the code gate is authoritative. Add one sentence telling the model that restricted/unverifiable ingredients are rejected downstream, so it doesn't argue with rejections.

### 3.5 `backend/gemini-agent/src/services/reverseScanService.ts`

Apply the same evaluator to recognized-food verdicts before they reach the phone (an item the household can't eat should be labelled as such, unknown ⇒ ask).

### 3.6 Tests

- `src/__tests__/recipeService.test.ts`: add cases for the reviewer examples — tamari (wheat+soy avoider) rejected; cream cheese (milk) rejected; lard/Worcestershire (vegetarian) rejected; generic tamari NOT accepted as gluten-free absent a label evidence entry; undeclared compound ingredient in instructions text rejected; unknown-ingredient rejection with "ask the user" path. Assert the rejection at the **wrapper** level, not only the evaluator:

```ts
it("rejects a recipe containing cream cheese for a milk-allergic household at the screen level", () => {
  const policy = ingredientPolicyFor(requestWithRestrictions(["milk"]));
  expect(firstRestrictedFood("fold in the cream cheese", policy))
    .toEqual({ food: "cream cheese", violation: expect.stringContaining("milk") });
});

it("returns a rejection — never undefined — when an ingredient has no facts at all", () => {
  const policy = ingredientPolicyFor(requestWithRestrictions(["milk"]));
  expect(firstRestrictedFood("whisk in shoyu", policy)?.violation)
    .toContain("unknown-ingredient-facts");
});
```
- Session-level: two eaters with disjoint restrictions must union (e.g. one `glutenFree`, one `dairyFree` ⇒ both screened).
