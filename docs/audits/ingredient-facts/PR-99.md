## 2. Fail-open behavior found

1. **Unmatched restriction targets block nothing.** `Catalog.blockedIngredients(target:)` (lines 173–187) matches an ingredient by exact id/name equality plus the `allergenGroups` map; if nothing matches it returns an **empty set with no error**. A restriction recorded as `"peanut"` (the allergen) matches no ingredient in the 50-core catalog (`peanut_butter` is the id/name that exists) and no group unless the catalog was constructed with a `peanuts` group — result: zero recipes blocked, engine reports success.
2. **Diet restrictions are no-ops.** `blockedIngredients` never consults `CatalogRecipe.hasTag`, so diet targets — `"vegetarian"`, `"vegan"` — expand to an empty set (no ingredient is named "vegetarian"). `Ranker.blockedIngredients(now:)` unions them in happily; a vegetarian household is ranked recipes containing meat, lard, Worcestershire sauce. The tags exist on recipes (`vegetarian`, `vegan` bits in `CatalogTag`) but the filter ignores them.
3. **`allergenGroups` defaults to `[:]`.** Line 158: `allergenGroups: [String: Set<IngredientID>] = [:]`. Whoever builds the catalog decides what "peanuts" or "tree nuts" covers, from an ad-hoc literal, not from a shared dataset. A catalog built without the map silently disables every group-level restriction.
4. **Compounds resolve only if a catalog row exactly matches.** A `"soy sauce"` allergy blocks the `soy_sauce` row but not tamari (no such catalog row), hoisin, or teriyaki — same dish, same proteins, passes the filter. The blocker set is built from the 50-core catalog's identity strings, so any product/synonym outside them is allowed.
5. **No unknown state.** The filter's only outcome per candidate is blocked/pass. An ingredient whose composition is unknown (stock cube, "seasoning blend") is passable by construction; the engine cannot say "ask the user".

## 3. Exact changes needed (file by file)

Goal: the hard filter evaluates ingredient **facts**, not string identity; unknown ⇒ ask the user; meal restrictions are the union of every eater's restrictions (`FLRestrictions.union`).

### 3.1 `packages/FLTaste/Package.swift`

Add the dependency:

```swift
dependencies: [
  .package(path: "../FLIngredientFacts")
],
targets: [
  .target(name: "FLTaste", dependencies: ["FLIngredientFacts"]),
]
```

(Adjust the relative path to where the package lives in the join; keep FLTaste Foundation-only — FLIngredientFacts is Foundation-only too.)

### 3.2 `packages/FLTaste/Sources/FLTaste/Features/Catalog.swift`

- Change `blockedIngredients(target:)` from string matching to facts evaluation. The catalog keeps only ingredient identities; restriction semantics move to the store:

```swift
// before
public func blockedIngredients(target: String) -> Set<IngredientID> { /* name/id/group match → Set */ }

// after — the Ranker asks the store per ingredient
public func isBlocked(_ ingredientName: String, restrictions: FLRestrictions, store: FLIngredientFactsStore) -> FLBlocked {
  switch store.evaluate(ingredient: ingredientName, restrictions: restrictions) {
  case .violated:  return .hard
  case .unknown:   return .ask   // fail closed: remove from ranked output, surface for confirmation
  case .allowed:   return .pass
  }
}
```

- Delete `allergenGroups` (and its `[:]` default) — group membership is a fact about ingredients and belongs in `data/ingredient-facts/facts.json` with evidence, not in a constructor parameter.

### 3.3 `packages/FLTaste/Sources/FLTaste/Model/Ranker.swift`

- `blockedIngredients(now:)` keeps its union shape (household + every eater — that part already matches `FLRestrictions.union`) but must resolve each `Restriction.target` into `FLRestrictions` (allergen names via the `FLAllergen` vocabulary, diets via `FLDiet`). An unparseable target today silently filters nothing; after the change it must produce a `.unknown`/ask outcome — never an empty blocked set.
- `rank(_:rng:)`: switch candidate filtering from `used.isDisjoint(with: blocked.hard)` to per-ingredient evaluation as in 3.2; `.ask` candidates are dropped from ranking and reported in a new `rankedOutPendingConfirmation` output so the app can ask.

### 3.4 `packages/FLTaste/Sources/FLTaste/Events/TasteEvent.swift`

Keep `Restriction` as the persisted event shape, but validate `target` at the fold boundary (`Fold.apply`): allergy targets must normalize to an `FLAllergen` case or a resolvable ingredient identity; diet targets to an `FLDiet` case. Unmappable targets are surfaced (profile shows "unrecognized restriction"), not silently accepted-and-ignored.

### 3.5 Tests (`packages/FLTaste/Tests/FLTasteTests/`)

- `FeatureTests`/`ModelTests`: construct the catalog from the fixtures **without** an `allergenGroups` literal and assert the reviewer examples: peanut restriction blocks peanut_butter recipes; `"vegetarian"` blocks meat-containing recipes; tamari is blocked for a wheat+soy eater even though no tamari row exists (resolved via facts, fail closed); a candidate with an unknown-composition ingredient is flagged ask-not-rank; two eaters' restrictions union (one `milk`, one `glutenFree` ⇒ cream cheese and generic tamari both filtered).
