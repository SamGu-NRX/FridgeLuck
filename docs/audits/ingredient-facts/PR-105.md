## 2. Fail-open behavior found

1. **The sim's catalog disables group restrictions by construction.** `CatalogLoader.load` line 119 builds `RecipeCatalog(ingredients:recipes:)` and never passes `allergenGroups`, which defaults to `[:]` (FLTaste `Catalog.swift` line 158). Every allergy drawn by `drawRestrictions` (line 180) can therefore only block an ingredient via **exact id/name match** — group-level expansion (e.g. an allergy to "tree nuts" covering almond-related rows) is structurally impossible in the simulator.
2. **Generated diet restrictions are no-ops.** `drawDiet` (line 195) and `Dynamics` diet shifts (line 54) emit targets `"vegetarian"`/`"vegan"`. FLTaste's `blockedIngredients(target:)` matches only ingredient ids/names and group keys — no ingredient is named "vegetarian", and the filter never consults recipe tags — so these "hard restrictions" block **zero** recipes. The simulator generates households whose diet restrictions demonstrably change nothing about what is ranked, then records ground truth as if restrictions were in force.
3. **Allergy picks are drawn from names the catalog carries, not facts it carries.** `drawRestrictions` filters `allergyCandidates` to ids present in the catalog (`catalog.ingredients[IngredientID($0)] != nil`), so the sim can only ever exercise exact-name blocking. Compounds (tamari vs soy sauce) and unknown-composition ingredients are never simulated — the scenario space is exactly the one where the fail-open cannot be observed.
4. **Ground truth asserts enforcement the engine doesn't perform.** `GroundTruth`/`GroundTruthJSON` serialize restrictions as if they were hard filters; downstream calibration against these runs will treat diet-restricted households as if they saw no restricted recipes. No unknown/ask state exists anywhere in the sim's outcome model.

## 3. Exact changes needed (file by file)

Goal: the simulator exercises the **real** fail-closed filter — facts from `data/ingredient-facts`, unknown ⇒ ask-the-user outcomes modeled, meal restrictions the union of every eater's (`FLRestrictions.union`).

### 3.1 `packages/FLTaste/Sim/Package.swift`

```swift
targets: [
  .target(name: "FLTasteSim", dependencies: ["FLTaste", "FLIngredientFacts"]),
]
```

(plus the `.package(path:)` reference to the FLIngredientFacts package.)

### 3.2 `packages/FLTaste/Sim/Sources/FLTasteSim/CatalogLoader.swift`

Thread the facts store through the loader:

```swift
// before (line 119)
return RecipeCatalog(ingredients: ingredients, recipes: recipes)

// after
let store = try FLIngredientFactsStore(dataDirectory: dataDirectory) // sim input points at data/ingredient-facts
return RecipeCatalog(ingredients: ingredients, recipes: recipes, facts: store)
```

(the `RecipeCatalog` change itself is the PR #99 fix — 3.2 of its fix list; this PR must pass the store in rather than relying on the `[:]` default.)

### 3.3 `packages/FLTaste/Sim/Sources/FLTasteSim/Household.swift`

- `drawRestrictions` (line 180): draw allergy targets from the **facts vocabulary** (`FLAllergen` cases) in addition to catalog ingredient names, so group-level blocking and compound resolution are exercised.
- `drawDiet` (line 195): keep the targets but express them as `FLDiet` cases so the filter can expand them (per the PR #99 fix, diet restrictions filter via facts/tags, not name equality).
- `restrictionUnion` (line 32): replace the hand-rolled dedupe union with `FLRestrictions.union` once restriction state carries `FLRestrictions` — same semantics, shared code path.

### 3.4 `packages/FLTaste/Sim/Sources/FLTasteSim/Dynamics.swift`

Diet shifts (lines 51–57) apply the new restriction form; a shift to an unrecognized diet target must surface as an ask-the-user/unknown outcome in the sim's world state, not a silent no-op.

### 3.5 `packages/FLTaste/Sim/Sources/FLTasteSim/GroundTruth.swift` (+ `GroundTruthJSON.swift`)

Record **outcomes**, not just intent: per simulated meal, which ingredients were blocked, which were ask-the-user (unknown facts), and which were served. Calibration consumers then see the fail-closed behavior they will meet in the engine.

### 3.6 Tests (`packages/FLTaste/Sim/Tests/SimTests/`)

- `GenerationTests`: a household drawn with a `milk` allergy must never be served a recipe whose facts resolve cream cheese (and vice versa for tamari/wheat+soy); vegetarian/vegan households must show restricted recipes actually filtered — the current suite cannot detect this, so add the assertion.
- `SimulatorTests`: at least one scenario with an unknown-composition pantry item exercises the ask-the-user outcome end to end.
