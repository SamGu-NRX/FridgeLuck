## 2. Fail-open behavior found

1. **Missing record or empty `classes` ⇒ allowed.** `Lookup.swift` line 42/46: `ingredients[key]?.classes ?? []` — a substitute absent from the ingredient registry, or one of the **211 of 381** records whose `classes` array is empty, is evaluated as "carries nothing" and passes every restriction check. Absence of data is treated as evidence of safety, the exact inverse of fail-closed.
2. **`tamari` is classed gluten-free without evidence — divergent from soy sauce.** In `pairs.json`: `tamari → ["soy"]` while `soy_sauce → ["gluten","soy"]`. Generic tamari carries soy with wheat/gluten **unknown unless product evidence** exists; the table silently encodes it as gluten-free. A `gluten-free` swap to tamari passes the recheck with no `label` evidence behind it. The same divergence pattern must be audited for other variable-composition products (stock cubes, bouillon).
3. **`lard` and `worcestershire` pass the vegetarian recheck.** The table's `vegetarian` restriction forbids only the flesh/meat classes (`meat_poultry`, `meat_ground`, `meat_whole_cut_pork`, `meat_whole_cut_red`, `flesh_fish`, `flesh_shellfish`). But `lard → ["animal_product"]` and `worcestershire → ["animal_product","fish"]` — **neither `animal_product` nor the `fish` allergen class is in vegetarian's `forbids`**. `swaps(for:role:restrictions:["vegetarian"])` happily offers lard and Worcestershire to vegetarians. (Vegan's list adds dairy/egg/honey but not `animal_product` either — bacon fat passes vegan the same way.)
4. **Two vocabularies for one reality.** The table's `AllergenClass` (18 cases, incl. flesh/meat classes and markers) and restriction registry are separate from `FLRestrictions`' `FLAllergen` (9) + `FLDiet` (5). Every other module reads its own lists (see the sibling fix lists); nothing forces these to agree. `RestrictionSet` throwing on unknown restriction *names* is good, but the vocabulary itself drifts.
5. **No unknown state.** `AllergenRecheck` has no "composition unknown" verdict — an unreviewed ingredient is indistinguishable from a verified-safe one, and `EvidenceStatus.unknown` covers only ratio/function claims, not composition.

## 3. Exact changes needed (file by file)

Goal: composition facts come from one dataset; unknown ⇒ ask the user; restriction semantics shared; the reviewer examples become conformance cases.

### 3.1 `data/substitutions/pairs.json` (or a migration away from it)

- **Fix the divergent entries now:** `tamari` must carry `["soy"]` plus gluten **unknown** — in the shared facts vocabulary that is soy-certain, gluten-unknown (a certified GF tamari product is a distinct preparation/product-form entry with a `label` evidence claim). `lard`, `bacon_fat`, `worcestershire` must carry classes that `vegetarian`/`vegan` actually forbid (`animal_product` must be added to both `forbids` lists, or the entries must carry the flesh classes where true — Worcestershire carries fish).
- **Add `vegetarian`/`vegan` forbids for `animal_product` and reconcile `fish` vs `flesh_fish`** so the class an ingredient carries is always covered by the restrictions that should exclude it.
- **Drive the 211 empty-class records to reviewed facts or explicit unknowns** — the shared dataset's `facts.json` already tracks certainty levels (`certain`/`typical`/`variable`/`unknown`); empty is not a state an ingredient may be in.

### 3.2 `packages/FLSubstitutions/Package.swift`

```swift
targets: [
  .target(name: "FLSubstitutions", dependencies: ["FLIngredientFacts"]),
]
```

### 3.3 `packages/FLSubstitutions/Sources/FLSubstitutions/Model.swift` + `Vocabulary.swift`

Map `AllergenClass` → `FLAllergen`/`FLDiet` (or replace it): the flesh/meat classes and `animal_product`/`honey` markers are diet facts and belong in the shared diet vocabulary; the nine contract classes map to `FLAllergen`. Keep the marker classes only as evidence labels.

### 3.4 `packages/FLSubstitutions/Sources/FLSubstitutions/Lookup.swift`

Replace the class-list intersection with store evaluation:

```swift
// before
let substituteClasses = sortedClasses(ingredients[pair.substitute]?.classes ?? [])   // FAIL-OPEN: missing ⇒ []
let violated = sortedClasses(substituteClasses.filter { restrictionSet.forbidden.contains($0) })

// after
let meal = restrictionSet.flRestrictions                  // shared vocabulary
switch store.evaluate(ingredient: pair.substitute, restrictions: meal) {
case .allowed:       /* keep candidate */
case .violated(let v): /* refuse: reason names the offending component */
case .unknown:       /* fail closed: not offered; surface as "ask the user / confirm" */
}
```

`RestrictionSet` (Restrictions.swift) keeps name validation but its `forbids` become `FLRestrictions`; the both-sides recheck stays (the original side matters too when it is still on the plate).

### 3.5 `packages/FLSubstitutions/Sources/flsub-report/main.swift` + `data/substitutions/REPORT.md`

The coverage report should report **unknown-composition** ingredients as their own class (not silently safe), so the 211 shrink visibly.

### 3.6 Tests (`packages/FLSubstitutions/Tests/FLSubstitutionsTests/`)

- `AllergySweepTests`/`CompoundAllergenTests`: add the reviewer examples as first-class cases — `tamari` swap refused for `gluten-free` (no label evidence), `lard`/`worcestershire` refused for `vegetarian` and `vegan`, a substitute missing from the registry yields ask-the-user (never offered), and two eaters' restrictions union (milk + peanut ⇒ both screened).
