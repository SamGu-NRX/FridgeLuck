## 2. Fail-open behavior found

1. **The feasibility engine checks names, not properties.** Both call sites (lines 284 and 319) invoke `restriction.permits(canonicalName:)` with the allergen and diet arguments left at their defaults — so the check reduces to `customExclusions.contains(normalized(name))`. An ingredient is blocked **only** if the user hand-listed its exact canonical name. A milk-allergic household is feasibly served every recipe containing **cream cheese** unless someone typed "cream cheese" into custom exclusions; a wheat+soy household gets **tamari**; a vegetarian gets **lard** and **Worcestershire sauce**.
2. **The dataset needed for the check doesn't exist in this package.** `RecipeCatalog.swift` carries canonical names and quantities; there is no per-ingredient allergen/diet property anywhere in `FridgeLuckPantry`, so the engine *cannot* fail closed — it has nothing to consult.
3. **Swaps recheck on name only.** Line 319: a swap rescue passes when the substitute's canonical name misses `customExclusions`. A swap to a compound ingredient (soy sauce for a wheat+soy household) is accepted if no custom exclusion names it — SPEC 3.1's "every substitution rechecks all eaters' allergens, including compound ingredients" is not implementable on name matching.
4. **No unknown state.** `permits` returns Bool; an ingredient whose composition is unknown (stock cube, seasoning blend) is feasible-by-default. The suite-A property tests (200-pair audit) exercise quantities and preparation forms over this same name-only space, so they cannot detect any of the above.

## 3. Exact changes needed (file by file)

Goal: feasibility lines and swap rescues evaluate ingredient **facts**; unknown ⇒ ask the user (a `needsConfirmation` line state, never silently feasible); meal restrictions are the union of every eater's restrictions (`FLRestrictions.union`).

### 3.1 `packages/FridgeLuckPantry/Package.swift`

```swift
targets: [
  .target(name: "FLRecipeCore", dependencies: ["FLDomain", "FLIngredientFacts"]),
]
```

(plus the `.package(path:)` reference; FLIngredientFacts is Foundation-only and Linux-buildable like this package.)

### 3.2 `packages/FridgeLuckPantry/Sources/FLRecipeCore/PantryFeasibility.swift`

Thread a store through the engine and replace both name-only checks:

```swift
// before (line 284)
guard restriction.permits(canonicalName: line.ingredient.canonicalName) else {
  return try buildLine(..., state: .blockedByRestriction, ...)
}

// after
let meal = FLRestrictions.union(householdEaters.map(\.flRestrictions))   // every eater
switch store.evaluate(ingredient: line.ingredient.canonicalName, restrictions: meal) {
case .violated(let v):
  return try buildLine(..., state: .blockedByRestriction, reason: v.reason)
case .unknown(let u):
  return try buildLine(..., state: .needsConfirmation,
                       reason: "'\(line.ingredient.canonicalName)' needs confirmation: composition unknown")
case .allowed:
  break
}
```

- Add `needsConfirmation` to `FLFeasibilityLineState` (in `Feasibility.swift` next to `blockedByRestriction`, line 42): a hard stop for serving, but distinct from "forbidden" so the UI can ask instead of merely rejecting.
- Line 319 (swap rescue): the substitute must pass the **same** facts-based evaluation — `case .unknown` on the substitute downgrades the rescue to `needsConfirmation`, never auto-accepts; the existing "stale rescue never reserves" pattern is the template.

### 3.3 `packages/FridgeLuckCore/Sources/FLDomain/Restriction.swift`

As in the PR #103 fix list §3.2 (same file, shared package): remove `permits`' default arguments and add the facts-based `verdict(for:store:)` with `allowed | violated | unknown`. Pantry-feasibility then cannot regress to name-only checking by omission.

### 3.4 `packages/FridgeLuckPantry/Sources/FLRecipeCore/RecipeCatalog.swift`

Optionally cache resolved facts per canonical name to keep the 200-pair property tests fast; correctness comes from the store, not a local copy.

### 3.5 Tests (`packages/FridgeLuckPantry/Tests/FLRecipeCoreTests/`)

- `PantryFeasibilityTests`: reviewer examples — a milk-allergic household's cream-cheese line is `blockedByRestriction` (facts), not feasible; tamari blocked for wheat+soy; lard/Worcestershire blocked for vegetarian; a swap to a restricted substitute never rescues.
- `PantryFeasibilityPropertyTests`: extend the property space with an unknown-composition ingredient class — the engine must return `needsConfirmation` for every such line (fail-closed invariant), never `satisfied`.
