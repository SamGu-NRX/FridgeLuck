## 2. Fail-open behavior found

Every path here is an allow-by-default keyed on a **local 50-ingredient list**; anything the list doesn't name is treated as safe.

1. **Unknown IDs resolve to "no groups"** — `memberships(forCoreIngredientID:)` line 215: `coreMembershipByID[ingredientID]?.groups ?? []`. The doc comment says it plainly: unknown IDs "return an empty set: the curated table makes no claims about them." USDA-catalog ingredients (800 rows) and any recipe ingredient outside the bundled 50 are therefore never excluded. A wheat avoider is offered **tamari**; a milk avoider is offered **cream cheese**; neither appears in the 50-core table, so neither is ever blocked.
2. **Diet exclusions are a hardcoded 5-item list** — `HealthProfile.dietaryExcludedIngredientIds` lines 173–182: `if diet == "vegan" { excluded.formUnion([12, 13, 14, 32, 50]) }` (cheese, milk, butter, yogurt, sour cream). Egg (ID 1), honey, ground beef (ID 31), chicken breast (ID 33), salmon (ID 29) and canned tuna (ID 37) are **not** in the vegan list, so a vegan profile is offered recipes containing eggs and meat. `vegetarian`, `pescatarian` and `keto` return an empty set — the ingredient-level diet check is a no-op for them (a vegetarian is offered **lard** or **Worcestershire sauce** in any recipe; neither check fires).
3. **The recipe filter can only see the list** — `RecipeRepository` lines 122–127 filter recipes by ID membership in the exclusion set, then lines 130–198 append every surviving recipe. No per-ingredient property lookup exists: absence of an exclusion entry means "allowed". Compound ingredients are not decomposed (soy sauce is special-cased as soy+gluten in the table, but tamari, hoisin, teriyaki, worcestershire are not resolvable at all).
4. **Duplicate divergent lists** — allergen groups live in `AllergenGroupMembership.coreMemberships`, diet exclusions in `HealthProfile`, and recipe-tag gating in `requiredRecipeTagMask` (which, e.g., does nothing for pescatarian). Three vocabularies, no shared source of truth; the gluten-free diet does not exist as a selectable concept outside `AllergenGroupID.gluten` (wheat_gluten), and "gluten-free" is asserted per-ingredient in the table without product evidence (oats are blanket `.gluten`, generic tamari is absent entirely).

## 3. Exact changes needed (file by file)

Goal: replace the per-module lists with fail-closed evaluation from `FLIngredientFacts`; treat `unknown` as **ask the user**, never allowed; meal restrictions are the **union** of every eater's restrictions (`FLRestrictions.union`).

### 3.1 `apps/ios/Platform/Persistence/Bundle/BundledDataLoader.swift` (+ `Package.swift` / project target)

Add the facts store to app dependencies so every consumer shares one instance:

```swift
import FLIngredientFacts

public enum AppFactsError: Error { case datasetMissing }

public enum AppFacts {
  /// Loads the process-wide store from the bundled data/ingredient-facts copy.
  /// Throws at startup when the bundle or dataset is broken — a load failure is
  /// a launch error, never a silent fallback to the retired lists.
  public static func makeStore() throws -> FLIngredientFactsStore {
    guard let dataset = Bundle.main.resourceURL?.appendingPathComponent("data/ingredient-facts", isDirectory: true)
    else { throw AppFactsError.datasetMissing }
    return try FLIngredientFactsStore(dataDirectory: dataset)
  }
}

// consuming call site (App init / scene phase) — the startup error path:
do {
  let store = try AppFacts.makeStore()
  self.facts = store
} catch {
  // surface a startup error state to the user; never fall back to the old lists
}
```

Ship `data/ingredient-facts/identities.json` and `facts.json` as bundle resources (same path as `data.json`). `FLIngredientFactsStore.init(dataDirectory:)` throws if the dataset is missing — the `do/catch` above is the sanctioned handling; never force-unwrap the bundle URL and never fall back to the old lists.

### 3.3 `apps/ios/Platform/Persistence/Repository/RecipeRepository.swift` — move the gate to the recipe level

The exclusion gate at lines 122–127 filters ingredient IDs, and the load loop at lines 130–198 **appends every surviving recipe**. An ingredient-scoped fix is not enough: the append decision itself must become restriction-aware, or a recipe that clears the ID-set gate stays eligible no matter what the per-ingredient check says.

```swift
// before (lines 122–127): an ID-set filter, followed by appends at 130–198
let excludedIngredientIds = profile.effectiveAllergenExclusionIds.union(
  profile.dietaryExcludedIngredientIds)
...
if excludedIngredientIds.contains(ingredientID) { continue }

// after — a per-recipe verdict over ALL lines, decided before anything is appended:
enum RecipeVerdict: Equatable {
  case eligible
  case rejected(reason: String)           // hard restriction conflict — never ranked
  case needsConfirmation(reason: String)  // unknown facts — held for the user, never ranked
}

func recipeVerdict(
  _ recipe: Recipe, meal: FLRestrictions, store: FLIngredientFactsStore
) -> RecipeVerdict {
  var unknowns: [String] = []
  for ingredient in recipe.ingredients {
    switch store.evaluate(ingredient: ingredient.name, restrictions: meal) {
    case .violated(let v):
      // ONE forbidden line rejects the WHOLE recipe — return immediately.
      // A later allowed ingredient never rescues it.
      return .rejected(reason: v.reason)
    case .unknown(let u):
      unknowns.append("\(ingredient.name): \(u)")  // accumulate, keep scanning
    case .allowed:
      break
    }
  }
  return unknowns.isEmpty ? .eligible : .needsConfirmation(reason: unknowns.joined(separator: "; "))
}

// RecipeRepository.swift:130–198 — the append becomes conditional on the verdict:
for recipe in fetched {
  switch recipeVerdict(recipe, meal: meal, store: store) {
  case .eligible:
    results.append(recipe)
  case .rejected(let reason):
    continue  // drop the candidate; the reason feeds the debug/review UI
  case .needsConfirmation(let reason):
    pendingConfirmation.append(ConfirmableRecipe(recipe: recipe, reason: reason))
  }
}
```

Counterexample (the failure an ingredient-scoped `continue` preserves): recipe lines `pasta`, `cream cheese`, `basil` for a milk-allergic household. `pasta` → `.allowed`, `cream cheese` → `.violated` — the recipe is **rejected as a whole at that moment**; that `pasta` and `basil` evaluate `.allowed` later in the loop cannot rescue it. Symmetrically, `rice` + `seasoning blend` (no facts in the dataset) yields `.needsConfirmation` even though `rice` is allowed. An inner loop that `continue`s on `.violated`/`.unknown` would skip the cream cheese, finish on basil, and leave the recipe eligible — exactly the fail-open behavior this fix removes. Scanning order never changes the verdict: `.violated` returns immediately, and per the pinned semantics violated beats unknown.

`needsConfirmation` candidates are surfaced in the UI as "confirm with the user" (the existing review affordances in `Feature/Ingredients/IngredientReviewView.swift`), never silently ranked and never silently dropped.

### 3.4 `apps/ios/Domain/Allergens/AllergenGroupMembership.swift`

Keep `AllergenGroupID` and the versioned-preferences flow, but retire the hand-maintained `coreMemberships` table as an enforcement source. `memberships(forCoreIngredientID:)` and `effectiveExcludedIngredientIDs` become legacy shims that delegate to `AppFacts.store.evaluate` (or are deleted with their call sites). The table's evidence strings (FDA/EU bases) migrate into `data/ingredient-facts/facts.json` evidence entries rather than living in Swift.

### 3.5 `apps/ios/FeatureLogic/Recipe/ReverseScanFeatureLogic.swift` and swap/union call sites

Every "can I eat this?" verdict and every ingredient swap must run `store.evaluate(ingredient:restrictions:)` with the union of all eaters' restrictions; a swap whose substitute evaluates `unknown` asks the user. The comment in `AllergenGroupMembership.swift` ("Recipe generation and ingredient swaps should call the same functions") becomes literally true by pointing at the store.

### 3.6 Tests

Update `apps/ios/Tests/AllergenExclusionPolicyTests.swift`: the policy tests should assert fail-closed behavior at the **recipe** level — a recipe containing cream cheese plus otherwise-allowed lines is rejected as a whole (a later allowed ingredient does not rescue it); a recipe with an unknown-composition line is held for confirmation, not ranked; an ingredient absent from the dataset ⇒ not served. Add the reviewer examples: tamari blocked for wheat+soy; cream cheese blocked for milk; lard and Worcestershire blocked for vegetarian; generic tamari NOT gluten-free without a label-claim evidence entry; `FLRestrictions.union` meal semantics.
