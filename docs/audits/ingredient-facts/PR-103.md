## 2. Fail-open behavior found

1. **Undeclared allergens mean allowed.** `restrictionViolations` line 700: `let allergens = claims.allergensByIngredient[name] ?? []` — an ingredient with no entry in the caller-supplied claims map is evaluated as carrying **no allergens at all**. The claims are assertions by whoever builds `CandidateClaims`; nothing verifies them. A revision whose builder simply doesn't populate `allergenByIngredient` for tamari or cream cheese sails through a wheat+soy or milk household's dinner decision.
2. **Empty claims pass everything.** `CandidateClaims()` defaults to `allergensByIngredient: [:]` and `failingDietTags: []` (lines 87–89). A candidate carrying zero claims violates nothing — the review comment in `Tonight.swift` (lines 70–74, "the caller resolves compound ingredients to their declared allergen set... The flows never guess an allergen that was not declared") documents the fail-open as a policy: nothing declared ⇒ nothing forbidden.
3. **Diet failures are a caller assertion, not a computation.** `claims.failingDietTags` is intersected with the union restriction (line 705) — but nothing computes `failingDietTags` from the recipe's ingredients. A revision containing lard or Worcestershire sauce fails no `vegetarian` exclusion unless the caller declares it, and the default declares nothing.
4. **`permits` defaults invite the failure.** `permits(canonicalName:allergens:dietTags:)` (Restriction.swift lines 110–119) treats absent arguments as "no declared properties" — the type-level shape of fail-open. Callers inside this PR (e.g. `Tonight.swift:701`) rely on the defaults.
5. **No unknown state.** `permits` returns Bool. There is no way to express "this ingredient's composition is unknown — ask the user"; unknown composition is indistinguishable from verified-safe.

## 3. Exact changes needed (file by file)

Goal: restriction checks consult the shared facts dataset instead of caller claims; unknown ⇒ ask the user; the meal restriction stays the union of every eater's restrictions.

### 3.2 `packages/FridgeLuckCore/Sources/FLDomain/Restriction.swift`

- Make the restriction vocabulary interoperate with `FLIngredientFacts`:

```swift
import FLIngredientFacts

extension Restriction {
  /// This person's restrictions in the shared facts vocabulary.
  public var flRestrictions: FLRestrictions { /* map Allergen→FLAllergen, DietExclusion→FLDiet, keep customExclusions */ }
}
```

- **Remove the default arguments** from `permits(canonicalName:allergens:dietTags:)` (line 110) so no caller can silently claim "no allergens". Replace with an explicit facts-based verdict:

```swift
// before
public func permits(canonicalName: String, allergens: Set<Allergen> = [], dietTags: Set<DietExclusion> = []) -> Bool

// after — facts-driven, three-valued
public enum RestrictionVerdict { case allowed; case violated(String); case unknown(String) }
public func verdict(for canonicalName: String, store: FLIngredientFactsStore) -> RestrictionVerdict {
  switch store.evaluate(ingredient: canonicalName, restrictions: flRestrictions) {
  case .allowed:            return .allowed
  case .violated(let v):    return .violated(v.reason)
  case .unknown(let u):     return .unknown("composition unknown — ask the user")   // never allowed
  }
}
```

`customExclusions` name-matching stays (it complements facts-based evaluation).

### 3.3 `packages/FLFlowCore/Sources/FLFlowCore/Tonight.swift`

- Keep `unionRestriction` (line 58) — the union shape is right; map it through `flRestrictions` and evaluate with **one** store instance.
- `restrictionViolations(revision:claims:restriction:)` (line 692): replace `claims.allergensByIngredient[name] ?? []` with `store.evaluate(ingredient: name, restrictions: meal)` per required ingredient line:

```swift
// before
let allergens = claims.allergensByIngredient[name] ?? []
if !restriction.permits(canonicalName: name, allergens: allergens) { ... }

// after
switch restriction.verdict(for: name, store: store) {
case .violated(let why): violations.append("'\(name)' conflicts with a hard restriction: \(why)")
case .unknown(let why):  violations.append("'\(name)' needs confirmation: \(why)")  // ask, never serve
case .allowed: break
}
```

- `failingDietTags`: compute from facts (evaluate the revision's ingredients; a diet exclusion fails when any ingredient's diet facts say so) instead of trusting `claims.failingDietTags`. `CandidateClaims` loses `allergensByIngredient`/`failingDietTags` (or keeps them only as a cross-check that must be consistent with facts — a mismatch fails the candidate).
- Line 587's filter: candidates with `unknown` verdicts are held out of the accepted set and surfaced as "needs confirmation" options, never silently dropped **and** never silently served.
