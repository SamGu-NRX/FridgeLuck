## 2. Fail-open behavior found

1. **`isAllowed` defaults to allow.** `HealthProfile.swift` line 71: membership in the user's string lists is the only blocking mechanism; an ingredient absent from every list is allowed. The app has no ingredient-fact source at all in this PR — composition (cream cheese ⇒ milk, soy sauce ⇒ wheat+soy, lard/Worcestershire ⇒ animal products) is invisible to the check.
2. **The keyword expansion is a hardcoded, incomplete denylist.** `restrictionExpansion` returns gluten-coverage as the literal triple `[canonicalName, "soy sauce", "tamari"]` (lines 47–52). Everything not in that triple passes gluten-free: no `seitan`, no `stock cube`/`bouillon`, no barley/rye items, no compound coverage beyond one pairing. Diet and allergen restrictions get **no** expansion at all — only exact name matches.
3. **Unknown composition silently passes.** A scenario ingredient absent from the dataset is treated as allowed; there is no "unknown — ask the user" state anywhere in `Restrictions` or the scenario flow, so the join tests can never observe fail-closed behavior.
4. **No union semantics.** `Restrictions` is a single profile; multi-eater meals (the whole point of a household scenario join) have no way to combine two people's restrictions — each check sees one list.
5. **The special case is exactly where the reviewer looked.** It papers over the tamari case for gluten-free only, leaving the same failure shape open for every other restriction and ingredient pair (soy sauce offered to soy avoiders, cream cheese to milk avoiders, lard/Worcestershire to vegetarians).

## 3. Exact changes needed (file by file)

Goal: the scenario flows evaluate the shared facts dataset; unknown ⇒ ask the user; meal restrictions are the union of every eater's restrictions.

### 3.1 Package wiring

- `apps/ios` project generation (`project.yml` / XcodeGen): add the `FLIngredientFacts` product to the app target's package dependencies (local package reference to `packages/FLIngredientFacts` on this branch), so the app and its scenario tests link the shared module.
- If the scenario utilities are also built by a SwiftPM test target, add `FLIngredientFacts` to that target's dependencies in the same pass.

### 3.2 `apps/ios/Utilities/FLScenarioJoin.swift`

Delete `restrictionExpansion` (lines 33–57) — including the hardcoded gluten-free triple — and replace with store evaluation:

```swift
// before
func restrictionExpansion(_ restriction: String) -> [String] {
  // … keyword lists, special case "gluten-free" → [name, "soy sauce", "tamari"]
}

// after
import FLIngredientFacts

let facts = try FLIngredientFactsStore(
  dataDirectory: Bundle.main.url(forResource: "ingredient-facts", withExtension: nil)
    .map { Path($0.path) } ?? Path("data/ingredient-facts")   // bundle data/ingredient-facts with the app
)

func blockedByFacts(ingredient: String, meal: FLRestrictions) -> BlockedVerdict {
  switch facts.evaluate(ingredient: ingredient, restrictions: meal) {
  case .allowed:       return .no
  case .violated(let v): return .yes(reason: v.reason)
  case .unknown:        return .ask   // ask the user — never allowed
  }
}
```

Bundle `data/ingredient-facts` with the app (XcodeGen resource entry mirroring `data.json`), or load it from the repo checkout in test targets — the point is one dataset, not a keyword list.

### 3.3 `apps/ios/Models/HealthProfile.swift`

Same change as the app-suite fix list (§3.2 there): map `Restrictions` → `FLRestrictions`, back `isAllowed` with the store, and extend it to a three-valued result (`allowed | blocked | ask`). Keep the user's `custom` exclusions as an additional layer on top of facts.

### 3.4 `apps/ios/Services/AgentWorld.swift` (+ `DinnerPlan.swift`, `PantryService.swift`)

Every proactive surface/suppress decision and plan/pantry ingredient check goes through `blockedByFacts` with the **union** of the household's eaters' restrictions (`FLRestrictions.union`) — not the single-profile list. Ask-verdict ingredients surface as a clarifying question (the existing proactive question affordance), never as silent inclusion or suppression.

### 3.5 `apps/ios/ViewModels/PantryViewModel.swift` / `apps/ios/Views/Pantry/PantryView.swift`

Surface the ask state in the pantry UI (a "confirm composition" badge on unknown items) so the scenario join's ask outcome has a visible end point.

### 3.6 Tests (`apps/ios/ScenarioTests/` + unit tests)

- Replace expansion-list expectations with facts-based ones: gluten-free scenarios block tamari **and** stock cubes/seitan (not just the hardcoded triple); vegetarian scenarios block lard and Worcestershire; soy scenarios block soy sauce via compound resolution; a milk+peanut two-eater scenario exercises the union.
- Add an unknown-composition fixture: the flow must produce the ask outcome (and the pantry badge), never an allowed result.
