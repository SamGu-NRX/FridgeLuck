# Render matrix — every screen family × direction × appearance

Part 7 deliverable. This is the document Sam's final direction review
reads against the held render workflow
(`ci/pending-workflows/screens-renders.yml` — staged, not installed).

It answers one question for every screen state family: **what is verified
about this cell today, and where does the evidence live?**

## How to read a cell

Each screen state family has one row. For each direction (H = the
provisional default, P = Sam's approved pastel palette) and appearance
(light / dark, plus **cook** — the hob scheme the cook-mode surfaces
run), the cell carries TWO statuses:

| Mark | Meaning |
|---|---|
| **L** | **Pinned on Linux.** The colour layer of this cell is enforced by tests that run in this checkout: the direction's token table, the variant→table mapping, and the contrast floors. No Mac needed. |
| **N** | **UNVERIFIED-NATIVE.** The rendered appearance of this cell can only be verified where SwiftUI compiles — a Mac, or the held render workflow. Nothing in this repo has ever rendered it. |
| mock | A design mock shows this family in this direction/appearance — the render, when it runs, has a picture to match. Cited per row. |

Every cell in the matrix is **L** today (evidence below) and every cell
is **N** (no native render has happened for any of them). The mock
column is what varies: it says which picture exists to review against.
The matrix therefore separates the two questions a direction review must
answer — *are the colours right?* (answered, on Linux) and *does the
screen look right?* (pending the held workflow, by design).

## The Linux-pinned layer (applies to every cell)

- **Token tables.** `FLDesignTokens` carries the real H and P palette
  tables (`DirectionH.swift`, `DirectionP.swift`) for all three modes
  (light / dark / cook). `DirectionTokensTests` + `InvariantTests` +
  `CompletenessTests` pin their shape: 27 tests, 0 failures.
- **Contrast floors.** `DirectionContrastTests` re-computes each
  direction's documented contrast claims within a tenth
  (`direction-h/contrast-table.md`, generated by that round's
  `tools/contrast.mjs`; P's documented hexes incl. the four ADJUSTED
  text roles, `direction-p/DIRECTION.md` §5). Body-text floors are
  asserted in every scheme for every direction.
- **The mapping.** `FLRenderPaletteMapping` (`FLScreenSupport/
  FLPaletteVariant.swift`) resolves each variant to its own real table —
  `testEveryVariantResolvesAPaletteForEveryScheme` (H/P × paper/hob/dark
  = all six resolve), `testLandedMappingResolvesRealTables`,
  `testDirectionBasePaletteBridgeResolvesTheTenRoles`. The F scheme axis
  maps paper→light, hob→cook, dark→dark, so a screen running the hob
  scheme IS the cook cell of its row.
- **The Part 7 cross-screen lint** (`Part7RawSourceLintTests`) pins that
  no screen file names a direction type — every screen resolves colours
  through the theme, so the H↔P swap is a theme swap by construction
  (`FLScheme(.h)` / `(.p)`), and every cell of a row renders the SAME
  view tree over a different resolved palette.

Evidence per direction/appearance beyond the tables:
- **Mocks (H):** `docs/design-round/direction-h/<screen>.html` for every
  screen, every screen has a `-dark` sibling, `cook-lechef.html` shows
  the cook mode, `tonight-xxl.html` the large-type case. Every mock has
  a **States** section showing the family's states.
- **Mocks (P):** same layout under `docs/design-round/direction-p/`
  (incl. `-dark` siblings and `cook-lechef.html`).
- **Parts 2–6 notes:** `docs/screens/part{2..6}-notes.md` record each
  part's adaptation decisions per screen family.

## What remains native, and what closes it

- Every rendered pixel of every cell above is **UNVERIFIED-NATIVE**.
  The Linux checkout pins the COLOUR layer (tables, mapping, contrast)
  and the structure (lint suites); it cannot compile SwiftUI, so it
  cannot verify layout, dynamic type, or the rendered contrast of a
  composed screen.
- The held workflow `ci/pending-workflows/screens-renders.yml` is the
  staged verifier: per the package README it renders the shell screens
  on a macOS runner. When it is installed and green, every **N** in this
  matrix flips on its evidence — the review then compares each rendered
  cell against the mock cited in its row (plus `-dark` siblings and the
  two `cook-lechef` cook cells).
- Until then, this matrix is the honest statement: colour truth is
  tested here; appearance truth is staged, not claimed.
